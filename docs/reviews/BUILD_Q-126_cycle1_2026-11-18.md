## 3. Findings, by severity

### C1 -- MATERIAL: the ledger has no recorded clearance and no tamper evidence, so every clearance is an unauditable edit

`scripts/q126_calibrate.py:1510-1541` (`ledger_read`, `ledger_append`, `ledger_failures`) and `1617-1627`.

**The evidence.**
- Any non-"whole" line refuses the runner forever. No code path can append a clearance.
- The docstring (`:22-23`) says a failed line refuses "until the lead decides", and the plan's 6.2 lets a diagnosed
  defect go on at a new commit. To do that, the lead must delete or edit the line by hand, and the `*.failed` folder
  too.
- The result manifests carry nothing from the ledger, neither its lines, its hash nor its path. So the committed record
  of a result cannot show whether a failure was ever recorded and removed.

**The failure it allows.** A part fails a check: say a scalar mismatch at commit B. Someone deletes the failed line and
the folder, and reruns. If the rerun passes, the results are committed with no trace of the failure. The same happens
with a whole ledger and work folder deleted: a fresh start that escapes the reproduction rule. This is deliberate, not
ordinary, but it is exactly the act the lead's legitimate clearance will look like.

**The remedy (cheapest first, all before the first real line).**
1. **Chain each line.** Add `prev_sha256`: the sha256 of the previous line's bytes, or a fixed genesis string for the
   first. `ledger_read` refuses a broken chain as it refuses an unreadable line. About 10 lines. This catches an edit
   or a deletion anywhere but the tail.
2. **Anchor the head.** Each part's manifest and each result manifest records `ledger_head`: the line count and the
   sha256 of the file at write time. The choice and the criterion refuse if a part's recorded head is not a prefix of
   the current ledger. Every result manifest also carries the runner's ledger lines verbatim (some 10 to 20 short lines)
   and the absolute ledger path. This makes a deleted-ledger restart, or a `LOCALAPPDATA` redirect, visible in the
   committed files.
3. **Anchor outside the machine.** The driver prints the ledger head on every exit. The lead's routine PROGRESS line
   for each heavy exit quotes it. The auditor checks that each quoted head is a prefix of the ledger carried in the
   result manifests. This closes the last residual: truncating the tail before the next run.
4. **Make clearance a line, not an edit.** A subcommand, for example `--clear <failed line's sha256> --decision E-NNN`,
   refuses unless `DECISIONS.md` holds that row naming that sha256. It appends `{"outcome": "cleared", "clears": ...,
   "decision": ...}`, and `ledger_failures` ignores only failures cleared this way. The `*.failed` folder is renamed
   `*.failed-cleared-E-NNN` and kept.
5. **Tests:** an edited line refuses; a deleted middle line refuses; a part whose recorded head is not a prefix refuses
   at the choice; a clearance without its row refuses; a clearance with its row lets `preflight` pass.

**A related reading for the row.** Every clean run of a part writes a permanent whole record that every later run of
that part must reproduce, a timing measurement (R4 in my build read) included. Measure only at the run's final commit,
after these changes are merged. Otherwise the change from the measured commit to the run's commit has to reproduce the
measured part's output byte for byte.

### C2 -- MINOR: the choice's and the criterion's own ledger checks are untested at their call

`q126_calibrate.py:1908-1915` and `q126_validate.py:408-415`.

**The evidence.** Mutation M10 replaced the choice's `ledger_choice_problems(...)` call with an empty result. All 32
other tests of `test_q126_calibrate.py` passed. (Only `test_the_guard_on_this_repository` was deselected, because it
needs git refs, which the archive copy lacks.)
- `test_failed_checks_are_recorded_and_never_rerun` monkeypatches `ledger_choice_problems` away.
- The function itself is tested directly, but its call is not.
- I did not plant the same mutation in the validation, but no validation test calls `criterion_main` with a real
  ledger.

**The failure it allows.** A refactor drops the call, and the choice then accepts part folders that never passed
`finish_part`. Examples are folders copied in from another work folder at the same commit, or written by a hand-run
helper. The suite stays green.

**The remedy:** in `test_failed_checks_are_recorded_and_never_rerun`, or a new test, run `choice_main` and
`criterion_main` on work folders whose parts are whole on disk but missing from the ledger: expect REFUSED. Then run
them on parts that differ from an earlier whole record: expect FAILED_CHECK plus a `choice.failed` / `criterion.failed`
record.

### N1 -- NOTE: F3's record is circular, and its test passes with the forcing reverted

The forcing is correct, and `run_clean` forces it as well, so no run is at risk. To make the test able to fail, launch
a child process with `OMP_NUM_THREADS=2` that loads the script and prints the three variables, then assert "1". To make
the record mean something, record the live thread count. `threadpoolctl` is not installed (checked). `numpy`'s OpenBLAS
can report its count through `ctypes` (`openblas_get_num_threads`). Alternatively, state in the row that the record is
the configured value, not a measured one.

### N2 -- NOTE: three in-part refusals stay exit 3 with no record; safe under the ledger

These are `_manifest_base`'s seed-map check (`q126_calibrate.py:1765`, the same check `preflight` already passed) and
the core-output hash checks in `load_core_inputs` (`:1787`, `:1790`). Each refuses again on every rerun, and a rerun
core is held to its whole record. Also, `q126_validate.py`'s `main` does not catch `ProvenanceRefused` around
`part_main`. Such a raise there is a traceback exit 1 (a crash): never a pass, but a refusal recorded as a crash. One
`except CALQ.ProvenanceRefused` would make the exit codes agree with the calibration's.

### N3 -- NOTE: the prepared allow-list lines name unsharded files

If any frame is sharded at the write, the collection commit's entries must name `q126_cal_size__<part>.csv` and so on.
The pre-commit scan reports the shards by name, so this cannot pass silently. It is only a step for the lead's
collection checklist.

### N4 -- NOTE: defence in depth

`choice_main` and `criterion_main` do not call `failed_record_problems` themselves. They rely on `main`'s `preflight`.
A one-line call at the start of each costs nothing and covers any later caller.
