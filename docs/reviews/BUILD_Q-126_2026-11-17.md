## 1. Findings, by severity

### F1 -- MATERIAL: a reproduction failure is not kept, and the driver runs past it on its next invocation

`scripts/q126_calibrate.py:1805-1828` (`driver`), `1785-1802` (`prepare_part`), `1689-1703` (`choice_main`).

**The evidence.** I ran the runner's own `driver` on a synthetic work folder, with a stub step that writes each part
(script in my scratch folder; nothing under the tree):
1. All parts were written at commit B.
2. At commit C the probe's rerun differed. The driver printed `FAILED CHECK: a part rerun at a new commit does not
   reproduce its earlier output` and returned 5.
3. No `*.failed` record existed.
4. **Invoking the driver again returned 0.** It ran `drift` and `choice`. `prepare_part` saw the probe whole at commit
   C and returned "done", and the reproduction check lives only in the branch after a step that ran.

**Three other routes skip the comparison:**
- the hidden `--part <name>` entry, which never calls `prepare_part` or `reproduction_problems`;
- a fresh work folder after the fix, where there is no `.prev-*` to compare;
- an interruption between a part's exit and the driver's check.

`choice_main` checks only that each part is of the current commit (`part_problems`). It never looks at `.prev-*`.

**The failure it allows.** Suppose a code fix after a crash changes a part's numbers: a scope-D admission count, or a
sizing null's exact size. The plan says "otherwise the run stops". Here the operator's ordinary recovery (run the
command again) feeds the changed output into the choice. A fix would then act as a search over code. This is what
plan 6.2's third rule (the red team's m2 and m-1) exists to prevent.

**The remedy:**
- On any reproduction difference, write a failed record (for example `<part>.failed/` holding the differing names and
  hashes) before returning 5, so that `preflight` refuses from then on.
- `choice_main` runs `reproduction_problems` for every part that has a `.prev-*`, and refuses on any difference.
- Keep an append-only ledger outside the work folder: for example
  `%LOCALAPPDATA%\stage2-extended-runs\q126-calibrate.parts.jsonl`, one line per whole part with (part, commit, each data
  file's sha256). The choice refuses when a part's earlier-commit line disagrees with the current files. That closes
  the fresh-folder route.
- Refuse `--part` unless an environment token set by the driver is present.
- Add a test: the stub scenario above, then a second `driver` call that must return 5 and run nothing.

### F2 -- MATERIAL: some failed checks are not kept; `--work` bypasses the record

`scripts/q126_calibrate.py`:
- `1531-1536` (`preflight` reads `work_dir()`) against `1865` (`work = ... Path(a.work)`);
- `1704-1710` (the choice's failed check returns 5 with no record);
- `1664-1667` and `1615-1618` (the provenance refusal is exit 3 with no record).

`scripts/q126_validate.py`: `302-307` and `468` (the same `--work` split); `398-401` (the criterion's failed check has
no record).

**The evidence.** The code shows four gaps.
- **The choice's failed checks leave nothing behind.** These are: the nesting assertion over the whole table, the
  bad-subset counts rising in m, the probe's ranking re-check, the probed set, and NOT CHECKED for a missing null. They
  print `FAILED CHECK` and return 5, and nothing is written to the work folder. The next invocation finds every part
  "done" and runs the choice again.
- **Some failures are exceptions, not checks.** The alternating-model assertion and the `OverflowError` in
  `eligibility` and `_above` raise. The run exits 1, the code a crash gets, and the crash rule allows a rerun.
- **The validation's criterion step is the same.**
- **Two failed checks the plan names are exits 3 with no record.** Plan 6.2 lists "the provenance assertion" and "a
  count refused" among them; here both are refusals.
- **`preflight` looks for `*.failed` only in the default work folder.** The run itself uses `--work` when it is given.
  So `python scripts/q126_calibrate.py --work <another folder>` under `run_clean` recomputes every part, a failed one
  included, from nothing.

**The failure it allows.** The parts are deterministic at a commit, so a same-commit rerun mostly reproduces the same
failure. Exactness is not guaranteed across environments, though (F3: the BLAS thread count is not forced). A scalar
re-decision that disagrees by one rounding could pass on a rerun under another thread setting. The plan's rule is "a
failed check ... is never rerun"; as built, an ordinary invocation reruns it.

**The remedy:**
- Write `choice.failed/` and `criterion.failed/`, each a manifest with the failure text, before returning 5.
- Catch every exception in the choice and the criterion and turn it into a recorded failed check.
- Record a provenance refusal inside a part as a failed check too. (Refusing it at `preflight`, before any part
  starts, may stay a refusal.)
- Have `preflight` check the folder actually used, and every `q126-*.work*` under `RUNS_DIR`.
- Drop `--work` from the top-level command, or accept it only with the driver's token.

### F3 -- MINOR: the BLAS thread count is defaulted, not forced, and not recorded

`scripts/q126_calibrate.py:61-62` and `scripts/q126_validate.py:44-45` use `os.environ.setdefault(..., "1")`.
`CAL._versions()` records python, numpy, scipy and pandas, and no thread settings.

**The failure it allows.** A session with `OMP_NUM_THREADS=2`, which CLAUDE.md allows for workers, runs the
enumeration's matrix products (`Pk @ M`, `Pk @ VS`) with another summation order. A borderline cell can then flip.
Two things follow:
- after a code fix, a part can fail F1's reproduction rule for no defect, and stop a run of about a day;
- a scalar disagreement can depend on the session (F2).

**The remedy:** set the three variables to "1" unconditionally (CLAUDE.md: one BLAS thread per process). Record them,
and `numpy.show_config()`'s BLAS name, in each part's manifest, and have the choice refuse a mismatch as it refuses
other package versions.

### F4 -- MINOR: two declared checks can be weakened without a test failing

Each mutation was planted in a scratch copy, never in the worktree.

| mutation | where | result |
|---|---|---|
| `balance_ok`'s `<=` made `<` (the plan's "at most b") | `extended/lift_one_sample2.py:227` | **all 15 module tests pass** |
| `provenance_problems` stops checking `sample_entropy` | `scripts/q126_calibrate.py:592` | **the provenance tests pass**: the only plant on `sample_entropy` also changes `exact_index`, which refuses it first |
| the probe's condition `>=` made `>` | `scripts/q126_calibrate.py:1090` | caught: `test_condition_4_the_probe_at_its_failure_count` fails |
| the exact cells' balance denominator off by one session | `extended/lift_one_sample2.py:368` | caught: `test_the_enumerations_admission_against_the_scalar_cell_by_cell` fails |

**Why the boundary matters.** b_D on the judged block is the fraction 437/657 (held by
`test_the_balance_limits_and_runs_intervals_are_the_plans`), whose terms share no factor. So |side sum| / non-tie = b_D
only when every one of the 657 sessions is non-tie and |side sum| = 437. A 5,000-trade subset that trades every session
is plausible, so the boundary can bind on real cells.
- The scalar and vectorised forms share `balance_ok`, so the run's own re-decision cannot see an error there.
- `sample_entropy` only seeds the 20 uniform re-decision cells, so a wrong one cannot move a size. Still, the plan's 4.1
  asks for "the full entropy of every null".

**Also:**
- the end-to-end test's sizing part has no rejection, so the sizing re-decision runs only in its unit test;
- no test checks that every generator the run builds starts from a seed of the block.

**The remedy:**
- a boundary test: |s| = v and M = n admitted, |s| = v + 1 refused, in `admission2`, `admitted_matrix` and
  `exact_flip2`;
- a plant that changes only `sample_entropy`;
- a spy on `numpy.random.default_rng` during the end-to-end toy. It records every entropy passed, and the test asserts
  each one's first word is a seed of the toy block. This is the mechanical form of item 12's guarantee (section 2).

### F5 -- MINOR: the cells file is not bounded by construction; the licence guard will flag a new result file

`scripts/q126_calibrate.py:847-862` (`cell_rows`) and `1342-1350`; `extended/price_levels.py` (E-185).

**Is `q126_cal_cells.csv` under the 100 MB push limit?** Expected yes, by a wide margin; guaranteed no.

**What sets its size.** A null-pair (an exact null with one in-rule pair) is written when its size is above a quarter
of nominal at some k. It writes one row per cell rejecting at k = 13: rows lie between its weighted count / 2 and its
count. At L = 42 (5,505,024 weighted cells), a pair at nominal at k = 13 writes about 1,500 rows. At L = 63 it writes
about 70.

**Empirically the file is tiny:**
- **Q-108's two sets of 115 subsets.** I applied `cell_rows`' rule, with Q-108's counts, to the pairs Q-126 puts in
  the rule. Upper-bound stand-ins took the place of 1.125 and 1.375, and Q-108's scope D has no balance limit, so it
  over-counts. At most 8 and 12 rows came out, all on the alternating models for `cons` in scope D. Scaled to 3,300
  subsets that is a few hundred rows.
- **The 20 drift populations** (scenarios A, C, D, F, G and H) at L = 42 and 63, every pair in the rule: one population
  wrote 14 rows (`cons_m1.5` in scope Q at L = 63), and the rest wrote none.

**Where it could go wrong.** At about 90 bytes a row, the limit is about 1.1 million rows. That needs hundreds of
null-pairs at nominal at L = 42, or a few dozen far above it. Exactly the event the calibration looks for makes the
file grow, and it would arrive only at the choice, after about a day.

**The licence guard.** Its `level` rule flags `exact_index` in a frame shaped like `q126_cal_size.csv` (the core's
exact indices 0..33,019; share 0.51 on my synthetic frame). The pre-commit hook will refuse the file until a reasoned
allow-list entry is added. An entry cannot be added early, because a stale entry fails. My sizing-shaped frame was not
flagged, but only because the scanner reads the first rows, which hold the small indices.

**The remedy:**
- Before the first write, `choice_main` already checks every frame and name. Let it also compute each frame's CSV
  length. If any exceeds a declared ceiling (95 MB), shard that frame by part under names fixed now (for example
  `q126_cal_cells_<part>.csv`). This is a reading the lead records before the run, not a refusal: a refusal after a
  day's run would waste it.
- The lead plans the allow-list entries for the collection commit: `exact_index` and the count/denominator pairs, as for
  Q-108's files.

### F6 -- MINOR: the validation pins the module's blob, not the calibration runner's

**The remedy:** require `blobs[scripts/q126_calibrate.py]` to equal the calibration's as well, or record a reading

### F7 -- MINOR: the lock's hours and memory

**Hours.** I measured one subset-value's five exact enumerations at every candidate in both scopes, recording every
in-rule pair, on a 5,000-trade, 560-session synthetic population: L = 42 7.8 s, L = 55 0.8 s, L = 63 0.5 s, both
alternating models 0.01 s. That is about 9.1 s, with the 5-cell scalar re-decision on top. So:
- the sizing part is 3,185 x 2 x about 9.3 s, about 16.5 hours;
- the drift is 1,200 x 9.1 s, about 3.0 hours;
- with the plan's scaled core (4.3 h) and probe (2.3 h), **about 26 hours**.

That is the plan's own 25.3 h at eight candidates, above the builder's 22 h. The calibration also runs the guard again
at the start of every part (nine times).

**Memory.** The builder estimates 2.2 GB at the choice, against the plan's `--mem-gb 1.5`. That figure is the lock's
declared need ("as Q-108"), not a statistical rule. The choice concatenates about 660,000 rows. The core's long
columns (rate, interval and ratio for 12 levels) are NaN on every sizing and drift row, so most of the frame is NaN.

**The remedy:**
- take the lock with `--hours 30` and `--mem-gb 3`, set from a measured part, as a reading in the row;
- or slim the choice: compute eligibility from the parts' count columns only, and concatenate the long columns for the
  core and probe file alone.

Either way the plan is not changed.

## 2. The six named interpretations

**Item 1: the sizing and drift nulls in their own one-row-a-null files.** Faithful in content; a reading of the form.
- **Why the long form cannot be written.** At Q-108's bytes per row (27.06 MB over 50,420 rows, about 537 bytes), the
  sizing and drift nulls would take (31,850 + 6,000) x 16 rows, about 325 MB. That is past the 100 MB limit, so the
  split is needed.
- **The wide files are well under the limit.** `q126_cal_sizing.csv` carries, for every null: its fields, the
  denominator, the admitted weight, and the count at all 12 levels for all 16 (candidate, scope) pairs. Even at 7 digits
  in every count cell it is about 54 MB; realistically it is a few tens of MB.
- **What is dropped is derivable.** The rate, ratio, `admitted_share`, `cid` and `pair_in_rule` come from the counts
  and the module. The interval is blank on exact nulls anyway. The entropies come from 4.1 and the null's fields
  (`declared_entropies`). `trades_mean` and `nontie_sessions_mean` were never computed for these nulls (`long=False`).
- **Nothing the choice or the audit needs is lost.** The choice reads the parts, not these files. An auditor can rebuild
  every condition from `q126_cal_size.csv` and `q126_cal_sizing.csv`: the bad-subset counts pooled and per size and
  model, the zero-tolerance floor, and the probe's ranking scores.
- **What the row must record.** Plan 6.2 names four calibration files and 6.3 four validation files. The build writes
  `q126_cal_sizing.csv`, `q126_cal_drift.csv` and `q126_val_drift.csv` besides, so the row records the layout before the
  run.

**Item 3: the drift nulls are not re-decided by the scalar form.** Faithful. Plan 4.1's re-decision covers two sets:
the core's 1,170 exact nulls (100 cells and the 20 uniform) and the sizing nulls (5 cells). The drift nulls have no
exact null index and no seeded sample role. They decide nothing (3.3), and their enumeration is the code the other two
sets' re-decision checks.

**Item 4: "condition 1's sized part" and "the floor alone emptied a branch".** A sound literal reading.
- `c1_sized` is the third bullet of condition 1, no bad subset among the 3,300: the core's 115 subsets and the 3,185
  sizing subsets.
- "Refused by it alone" means it fails that bullet and passes everything else. "The floor alone emptied a branch" means
  the branch has no eligible candidate, but one would be eligible without that bullet.
- One caveat (F10): a candidate refused only by a bad *core* subset would also have been refused under Q-108's own
  per-subset floor, so that line does not measure the new sizing's cost alone. The table carries `bad_core_subsets` and
  `bad_sizing_subsets`, so the cost row should too.

**Item 9: the choice checks the probe's ranking again.** Faithful, and an addition that can only stop a run.
- It recomputes the ranking from the sizing parts and compares it with the probe part's `ranking.csv`: size, rank, j and
  the exact score as a string. It checks that the probed subsets are the ranked ones.
- The CSV round trip is safe. The scores are `str(Fraction)`, read back either as integers or as strings; ties go to
  the smaller j.
- A failure here is one of F2's unrecorded failed checks.

**Item 12: Q-108's code pinned by blob, through private copies whose retired maps raise.** Does this guarantee that no
old draw is reused? **Not by itself.** The retired maps guarantee only that the two named fallbacks (`null_plan()`,
`expected_counts()`) and Q-108's own part runner refuse. The guarantee rests on three things:
1. **The full-entropy assertion.** It runs before any read and any draw, at `preflight` and again in each part, the
   probe included once its ranking is known. It compares every `entropy`, `subset_entropy`, `sample_entropy` and exact
   index with 4.1's declared tuple, recomputed from the null's fields, and the first word must be a seed of the run's
   own block.
2. **The call graph.** Every draw site the run reaches takes its generator from those tuples: `run_mc`, `subset_index`,
   `_uniform_cells` and `drift_inputs_for`. The draws inside Q-16's `syn_batch` and Q-82's count-persistent engines go
   through the rng they are given.
3. **The first-word rule**, which makes a retired Q-108 entropy impossible.

I read the call graph. Code with other blocks' seeds is reachable but not called:
- Q-16's thinned `real_streams` draw;
- Q-82's `lift_streams` and C1' subsets.

Q-108's `fixed_streams` deliberately omits the thinned draw, and `Q82.Data(..., seeds={})` turns Q-82's seeded
properties into a KeyError, not a silent draw. So the guarantee holds for the code as built. F4's spy on
`default_rng` would make it hold mechanically. The blob pin is complete for the reused statistical code and matches
Q-108's manifests.

**Item 13: the regime-filter kind always returns "barred".** Faithful to E-187. `band_check("regime_filter", ...)` is
refused with the outcome "barred" on either block, before any side is read. The switching-side path stays open to every
family, as E-187 allows. `regime_filter_conditions` is kept for the tests and equals `q126_arith.regime_filter_check`
on the three gamed sides and the honest filter. W-1's hole is kept as pinned, which is harmless while the kind is
barred.
