### m-1 (minor): the accounting cannot see a trade the router declines, so an R mismatch runs silently to zero trades

- **Where.**
  - `extended/survey_route.py:73-77`, the docstring: "a trade ... with no outcome at the state's R (the vendored
    `no_outcome`, D-315), refuses -- so a NaN never passes silently".
  - `AccountingDraw.__call__`, lines 809-840.
  - `tests/survey_route_child.py:227-228` and `tests/test_survey_route.py:610-611`.
- **Evidence (vendored code, then a probe).**
  - The toy job (`scripts/early_look.py:478-480`) is `mode="rotation"`, `route_able=True`. Under it the router hands
    a trade to an account only if `drw.can_take(...)` holds (`shared_days.py:378-380`). `can_take` returns False when
    the trade has no finite outcome at the state's R (`sizing.py:494-496`). Such a trade is counted in the router's own
    `passed_over` / `skipped` and never reaches the draw. So the D-315 branch the accounting watches
    (`sizing.py:729-735`) is not reached for an R mismatch. The draw is still called on every slot, gets no trade
    index, and the accounting books `no_trade`.
  - **The probe.** It is in my scratchpad (`.../scratchpad/c3/probe.py`), on synthetic bars only. It uses the child's
    one-component RL3 table (w = 1.5, `r_1` padded as the child pads it), takes `check_policy_reads` out, and sets the
    policy to combine and funded at R = 1.0. `route_simulate` then **returned without a refusal**: two lanes, each
    tallied `{"no_trade": 130}`, nothing logged. That is round 1's failure ("every trade can go untaken, and the
    design reads as doing nothing"), passed through the accounting unrefused.
  - **The vacuous assertions.** `no_outcome == 0`, `nan_dropped == 0` and `sum(logged) == sum(map(len, logs))` (or
    `>= taken`) cannot be false when `route_simulate` returns. The first two are incremented only on the line before a
    raise. `check_taken_rr` returns each log's length.
- **Why this is minor, not blocking.**
  - **The policy check governs R.** Every R the lockstep reads into a draw comes from the decision's `rr`:
    `setr(dec.risk, dec.rr)` (`lockstep.py:1637-1643`), the collect phase's `set_risk(..., dec.rr)` (line 1745), and
    the second trade's `rr1` (line 1721).
  - **Every decision R is a leaf R.** The vendored policy nodes are `Leaf`, `Tiers` and `Phase` (`risk_policy.py`).
    `AfterWinPolicy` adds only flip decisions and risk changes (`after_win.py:140-160`). `check_policy_reads` walks
    every leaf of these and refuses any table-reading leaf whose R is not w (line 777 onwards).
  - **The fallback is refused.** The only fallback to the protocol leg's R is the router's holding clock when
    `dec.rr` is None (`lockstep.py:1784`). An `rr=None` trade is refused by the race at C2-6
    (`three_way_baseline.py:438`; see m-4).
  - **The check is always run.** `route_simulate` calls `check_policy_reads` before it builds anything, and the check
    is shown failing (the mixed policy; a leaf at R 1.0, which my probe also saw refused).
  - **So no input I could construct** reaches the gap without editing the module.
- **The failure it allows.** Any later change that lets a mismatched R past the policy check would give a design
  that trades nothing. Examples: a new node type, a multi-w reader for F-13, or a runner calling `TB.simulate`
  directly. Its accounting would read as clean, and the survey would score it as the do-nothing journey.
- **Remedy.** Do all of these:
  1. **A state-R check.** In `AccountingDraw.__call__`, refuse on every call when the draw's state R is set and is not
     the table's w: `inner._rr is not None and abs(inner._rr - w) > RR_TOL`. The draw is called on every slot even when
     the router hands it nothing (the probe's 130 calls a lane), so this reaches the case whatever the router does.
  2. **A planted mismatch in `check_race`.** Take the policy check out and set both leaves to R = 1.0. It must refuse;
     today it returns.
  3. **Reconcile.** Per lane, the tally's taken count should equal the race's booked records (see m-2). Replace the
     vacuous assertions with this.
  4. **The docstring.** Narrow lines 73-77 to what the accounting sees: the draws it is handed. Name the router's
     declines (D-318 `passed_over` and `skipped`, D-429 `skipped_busy`, D-339 `skipped_opposite`) as the engine's
     counts, outside the accounting. Line 59 already says "the vendored router passes a NaN trade on", which
     contradicts the present text.

### m-2 (minor): the tally's `taken` counts trades the race then leaves untaken

- **Where.** `AccountingDraw.__call__`, line 839. It is wrapped inside `RaceOver`, which calls it first
  (`three_way_baseline.py:345`).
- **Evidence.** After the accounting has booked `taken`, `RaceOver` can still return NaN in three cases:
  - an account whose day has ended (`st[2]`, lines 364-366: un-counted, and **not logged**);
  - `missed`;
  - `day_end` (`_law`).

  In the toy run none occurs: each lane's taken count is 28, its log has 28 records, and the laws are race and walk
  only. On a real job where the floor binds, `taken` would exceed the trades the race booked.
- **The failure it allows.** A runner or a page that reports the accounting's `taken` would overstate the trades
  taken. Nothing in this build decides on it.
- **Remedy.** Either rename it (`handed_to_race`), or fill `taken` from the lane's log after the race, with `missed`,
  `day_end` and the day-ended count apart. The day-ended count is the difference between the two.

### m-3 (minor): the `RaceOver` swap is safe for exceptions, re-entry and processes, but not for threads; no test shows the restore

- **Where.** `route_simulate`, lines 855-864.
- **Assessment.**
  - **The swap reaches the right door.** `replay`'s factories look `RaceOver` up as a module global when they are
    called (`three_way_baseline.py:623-624`). They are called only inside `simulate_lockstep_path`, which runs inside
    the `try`.
  - **Exceptions.** `finally` restores the original. In my probe it was the original after a normal run, after a
    `RouteRefused`, after the bypassed run and after the flip run.
  - **Re-entry.** Nested calls restore last-in first-out.
  - **Processes.** `multiprocessing` under spawn (Windows; macOS by default) re-imports the module in each child, so
    the swap never crosses a process.
  - **Other importers.** H4's scripts and tests call `TB.RaceOver(...)` only in their own processes, and nothing
    imports the name by value.
  - **The wrapper never changes an outcome.** `AccountingDraw` returns `out` unchanged or raises. So even a leak can
    only add a refusal or mis-tally; it never moves a number.
- **The hole: threads.** Two `route_simulate` calls in two threads can interleave like this:
  1. A saves the original.
  2. B saves A's wrapper.
  3. A restores the original.
  4. B restores A's wrapper, which then stays installed for the rest of the process.

  Then every later `TB.simulate` in that process runs under A's accounting, with A's table and A's `tallies`. That
  includes H4's runs and the baselines under "the same convention". The effect is a refusal (no_outcome on a v12-plan
  baseline, or a non-`TierSizedDraw`), or an `IndexError` on the lane. A concurrent `TB.simulate` in another thread is
  wrapped in the same way. Nothing in the survey or H4 threads `simulate` today.
- **Remedy.**
  - Capture the original once at import (`_RACE_OVER = TB.RaceOver`), and refuse on entry if `TB.RaceOver is not
    _RACE_OVER`. That catches a leak, a nested call or a concurrent call.
  - Hold a module lock around the swap.
  - Add one assertion to `check_race`: after the refused run, `TB.RaceOver is` the original.

### m-4 (minor): `rr=None` at w = 1 is admitted by both checks, but the race refuses it

    refuses it, and why it is admitted at all.
