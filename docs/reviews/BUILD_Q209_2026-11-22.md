# Red team: Q-208 and Q-209, the commit line's gate (wt/wt-report e859e24, a3a5b84), 2026-11-22

Read: `git diff 7edee2e a3a5b84 -- scripts/ tests/ .gitattributes` (the master merge 4b8cedd skipped),
`.claude/skills/merge-checklist/SKILL.md`, and the tests the selector should reach. The work was done in a detached
clone under `%LOCALAPPDATA%\stage2-extended-runs\rt-q209` (since removed) and in synthetic repositories in the
scratchpad. No commit was made, the real hook was never run, and no heavy run was started.

The brief said "T0 is the only tier that lands on master with no later T2". I set that claim aside and tested it. It is
false (F1).

## Verdict: **BLOCK**

T0 cannot be trusted to land records on master without a T2. There are two separate reasons:

1. **T0's selection is incomplete.** Three planted records-only commits were selected T0, and each skips a fast-tier
   test that then fails (F2).
2. **T0 does not stand on a T2-verified code state.** Even a complete T0 cannot carry this weight. On master, T0 runs
   on top of trees that no T2 ever tested:
   - a clean merge's result;
   - a cherry-pick;
   - a fast-forward.

   It then records `tier=T0` for those trees. Before Q-209, the next master commit's pre-commit ran the full tier on
   them (F1).

The merge gate can also be passed without a T2 on the exact merged tree, and parts of that leave no trace (F4).

## CHANGES-A-CONCLUSION

### F1. Master's code state is never required to have T2, and T0 now sits on top of it

**Where:**
- `scripts/fasttier_select.py:482-484` and `:500-503`: records-only commits are T0 in the main tree, judged only on
  `git diff --cached` against HEAD.
- `scripts/premerge_check.py:243-273`: the gate checks each merged *tip's* tree, never the merge result's tree.
- The claims `scripts/premerge_check.py:27` and `scripts/pre-merge-commit:14` ("the next commit's pre-commit fast tier
  still tests the merged tree in full") are false after Q-209.

**Evidence.** In a synthetic repository, git ran these hooks:

| Command | Hooks that ran |
|---|---|
| `git merge --no-ff X -m ...` (the checklist's command, SKILL.md:75) | `pre-merge-commit`, `commit-msg`, `post-merge`. No pre-commit and no post-commit, so no verdict for the merge tree. |
| `git cherry-pick`, `git revert`, `git rebase` | post-commit only (a NO VERDICT warning), no pre-commit. |
| `commit-tree` + `update-ref` | none. |

Amend laundering: I cherry-picked a code commit onto master, then ran `git commit --amend` with a `DECISIONS.md` row.
The pre-commit's `git diff --cached --name-only` printed only `DECISIONS.md`. The selector therefore returns T0, and
the hook records `tier=T0` for a tree that brings `extended/core.py` to master untested. post-commit then sees a
verdict and stays silent.

**Failure it allows.**
1. wt/a and wt/b each have a T2 tip. The lead merges both cleanly in sequence; the gate passes both.
2. The combined tree A+B has a semantic conflict. No hook ever runs T2 on it.
3. The lead's next commit, the decision rows, is records-only, so it runs T0 (a subset). It passes, and the defect
   sits on master unseen.

The checklist's manual `pytest` after the merge (step 6) is the only remaining guard, and it is procedure, not a gate.
Under E-207 this weakens a safeguard: before Q-209 that records commit ran the full tier.

**Remedy (any one closes it; the first is cheapest):**
- (a) In `decide()`, allow T0 in the main tree only when the diff from the nearest T2-verified tree to the commit's
  index tree is records-only. To find that tree, walk HEAD's first parents to the first tree for which
  `check_verdicts.tree_has_t2` is true, then run `git diff --name-only <that tree> <write-tree>`. Otherwise, T2. This
  also closes the amend and cherry-pick cases.
- (b) In the gate, require T2 on the merge result's own tree (`git write-tree` in pre-merge-commit; the index holds
  the result). Otherwise refuse with "merge with `--no-commit`, then commit (T2)".
- In either case, correct `premerge_check.py:27` and `pre-merge-commit:14`.

### F2. T0 misses whole-tree `git grep` scans, and counts non-Markdown files as records

**Where:**

- `:71` and `:155-158`: `docs/reviews/` and `docs/audits/` are records whatever their suffix (`.py`, `.json`, `.txt`).
  The docstring at `:9` says "a Markdown record".
- The docstring at `:51-55` lists git dependence only as history. `git grep` reads the working tree.

**Evidence: three planted records-only commits, each selected T0, each failing a skipped test.** Each was staged in the

The selector's regex-escaped names also hide records: `"DECISIONS\.md"` is normalised to `DECISIONS/.md` (`_norm`

**Failure it allows.** The lead commits a plan or a parking-lot note that quotes a family's seed (a routine thing to

- Restrict `RECORD_DIRS` to `*.md`. A `.py`, `.json` or `.txt` under `docs/` is then code, and T2 in the main tree.
- Add P1, P2 and P3 as tests of `tests/test_fasttier_select.py` on this repository.
- Better still, run every test that calls `git grep` on `ROOT` in every T0, as T0_ALWAYS.

### F4. The merge gate can be passed without a T2 on the merged tip, and some routes leave no trace

**Where:** `scripts/premerge_check.py:254-273`, `scripts/pre-merge-commit`. Hooks observed in the synthetic repository:

| Route | What happened |
|---|---|
| Fast-forward (`--ff-only`, or a default merge when ff is possible) | Only `post-merge` ran. No gate. |
| `git merge --no-verify` | Neither `pre-merge-commit` nor `commit-msg` ran, and post-commit never runs on a merge. The result is a merge with no verdict, exactly like a gated clean merge, so it cannot be detected afterwards. |
| Preset `GIT_REFLOG_ACTION` | git keeps a preset value (it calls `setenv(..., 0)`, without overwrite). `GIT_REFLOG_ACTION="merge b1" git merge --no-ff b4` reached the hook as `RA=[merge b1]`, so the gate checks b1's tip, not b4's. Called directly on a synthetic log, `merge_gate` returned None for "merge good" and refused "merge bad", "merge good bad" and "merge -- bad". |
| `git pull` | `"pull ..."` is refused (fail-closed). |
| Squash + commit | MERGE_HEAD absent, so main-tree code is T2 on the exact tree (fine); a records-only squash is T0 (F1, F2). |
| Cherry-pick, rebase, revert, commit-tree | No pre-commit (F1). |

`commit-msg` does run on a merge, with MERGE_HEAD present (`MH=y` in the log).

**Remedy:**
- Run the gate in `commit-msg` as well, from MERGE_HEAD's exact SHAs. This needs no environment parsing and no race
  (see also F13).
- Have the gate append a line `<merge tree>\tgate=ok\ttips=<shas>` to the verdict log.
- Have the installer set `merge.ff=false` in the main tree.
- Add `check_verdicts --first-parent <last-checked>..master` to the checklist and to `post-merge`. It should flag every
  merge without a gate line and every non-merge advance with no T2 or T0-on-T2 (F1).

### F5. Hook-written T2 verdicts key the index tree, but the tests read the working tree

**Where:** `scripts/pre-commit` has no index-versus-worktree check. Grep for `git diff`, `diff-files` and `stash` finds
none. Q-209 makes `check_verdicts.tree_has_t2` and the merge gate trust any `tier=T2` line, including one written by
pre-commit. `fasttier_full.py` refuses a dirty tree; pre-commit does not.

**Failure it allows.** A worker stages a broken half with `git add -p` and leaves the fix unstaged. A T2 commit (a
fallback, or a selection over 60 %) passes on the working tree. The broken index tree gets `tier=T2`, and the gate
admits it.

**Remedy.** Pre-commit records `tier=T2` (or `T1`, `T0`) only when `git diff --name-only` is empty and no untracked
file a test could read exists, as `premerge_check.dirty_checked_files` does. Otherwise refuse, or record `tier=dirty`,
which the tip rule rejects.

### F6. The lanes' memory accounting is per lane, and T0 is not a short run

**Where:** `scripts/fasttier_lock.py:596-599`. `acquire` surveys only its own lane's slots. With nothing running in
the T0 lane, `ok = True` and only the 1.5 GB wait follows. A full lane's second slot likewise ignores a T0 holder.
`decide` applies no FULL_FRACTION to T0 (`fasttier_select.py:500-503`).

**Evidence:**
- T0 for `DECISIONS.md` on this repository selects 120 of 155 test files (STATUS.md 44, PARKING_LOT.md 43, a review 50,
  a lever table 69). It is a near-full run in the "short-run" lane.
- `SLOT_RESERVE_SOURCE` records one fast tier peaking at 2.26 GB, with machine-wide available memory falling to
  0.018 GB.

**Failure it allows.**
- Two T2s run in the full lane, and a lead's DECISIONS T0 starts beside them at 1.5 GB free. That is Q-155's
  MemoryError / WinError 1455 condition. xdist's `fast_tiers_beside` counts both lanes' workers when choosing n, but
  the slot admission itself does not.
- Every commit's pre-flight queues on the one T0 slot. A 120-file T0 therefore delays every T2's pre-flight, so
  "never behind a full run" fails in effect. This is not starvation: lines time out and refuse.

**Remedy:**
- `acquire`'s `need` sums the reserves of running slots in both lanes.
- A T0 selection above FULL_FRACTION (or above a declared file count) runs in the full lane.
- Optionally, give the pre-flight its own slot.

### F11. `pre-merge-commit` lacks pre-commit's cross-tree guard, and the checker judges itself

- With `GIT_WORK_TREE` inherited, `TOP` is another tree, and `is_main_worktree` is evaluated there, so the gate is
  skipped.
- It runs `scripts/premerge_check.py` from the merge result, so a branch that changes `merge_gate` is judged by its
  own code. The same holds for `fasttier_select.py` in pre-commit: the staged selector decides its own fallback.

**Remedy:** copy pre-commit's OWN/TOP check. Run the checker from `git show HEAD:scripts/premerge_check.py`, or force
`--no-commit` + T2 when a merge touches `premerge_check.py`, `check_verdicts.py`, `fasttier_*` or `scripts/pre-*`.

### F12. `fasttier_full.dirt()` ignores some untracked files

`scripts/fasttier_full.py:48-58`: untracked files outside WATCHED (`results/`, `docs/calibration/`, `data/`, the
records) do not count. Such a file can make a tip's T2 pass that the committed tree fails.

**Remedy:** refuse on any untracked, non-ignored file, or run in a detached clean checkout (`run_clean`).

### F13. The gate resolves branch names at hook time

`premerge_check.py:264-266`. A branch that moves between the merge's computation and the hook is checked at the wrong
SHA.

**Remedy:** MERGE_HEAD in commit-msg (F4).
