## 4. Findings

### c3-1 (MINOR). The power-target check is circular unless the run's commit is pinned to the declaration's

**Where:** declaration 127-130.

**What it says.** The power target is "`MDL_POWER`'s value **at the run's commit**", and `git_commit` is "the clean
checkout's commit, **the one the pinning row names**".

**Evidence.**
- `wave42_apply.py` 211 records `power_target = R.POWER_TARGET`. That is `MDL_POWER` as imported at the run's own
  commit.
- So the check "equals `MDL_POWER` at the run's commit" holds at every commit, by construction.
- The `git_commit` item does not say that commit must be the one at which W42-R1 was pinned. "The pinning row" can be
  read as the values' own row, which is written after the run and names whatever commit ran. My remedy (i) in c2
  asked for "the pinning commit, or one whose diff from it touches no file the script imports". That clause was
  dropped.
- The fee item is not circular: it also checks the ledger's `subscription_fee` at `ledger_sha256`.

**The failure it allows.** A later commit edits `family_stats.MDL_POWER` from 0.8 to 0.9. An application from a clean
checkout of that commit writes `power_target` 0.9 and a z_L, limits and J_needed that move with it. Every item on the
audit list passes.

What would catch it:
- `constants.POWER_TARGET` differing from section 2's table value (`0.8`, declaration 262). The audit list does not
  ask for that comparison.
- `rule_module_sha256`, but only if `wave42.py` itself changed, and here it did not.

It needs a committed edit, which git shows, so it is not a silent forgery.

**Remedy (text only, before the pin).** Replace "at the run's commit" with "**equals section 2's table** (`0.8`), and
the output's `constants` equal section 2's table". Add to the `git_commit` item: "**the commit W42-R1's pinning row
names, or a descendant whose diff from it touches none of the files the script imports** (`extended/wave42.py`,
`scripts/wave42_apply.py`, `extended/levers_terms.py`, `extended/family_stats.py`, `extended/search_calendar.py`,
`extended/h4_collect.py`, `extended/results.py`)".

### c3-2 (MINOR). `pinned_inputs` is the survey's documented entry point, and none of its values is tested

**Where:** `wave42.py` 553-559; declaration 9.2, "`pinned_inputs(values)` ... what a design is scored with".

**Evidence.** Three mutants of mine survive the full test files (142 passed):
- **A:** `pinned_inputs`' weights replaced by equal weights over all six dimensions. This is wrong in the fallback
  form, where the weights are `{"money": 1.0}`.
- **B:** `pinned_inputs`' B set to the first budget, not B\*.
- **C:** every cap's `hi` widened by 1.

The tests check only `pinned_inputs`' key set and its `floor` (`test_the_output_file_has_the_declared_row_schema...`).
`test_a_design_that_never_passes...` uses `P["B"]` and `P["caps"]`, but only for cost, whose z is 0 whatever the
caps. `setting_rule` never calls `pinned_inputs`, so C-1's "the survey runs the rule's own code" does not reach these
three values.

**The failure it allows.** Suppose the survey scores a design through `unit_scores(d, P["B"], P["caps"])` or reports
its per-dimension z. A defect in `pinned_inputs` would then give values that differ from the rule's, and no test would
fail. A survey that calls `composite_per_seed(values, ...)` instead is not exposed, because that path reads
`_scoring`, which the rule uses.

**Remedy (test only; the tests are outside the pin).** In both forms (`base` and the fallback), assert:
- `pinned_inputs(V)["B"] == V["budgets"]["primary"]`;
- `["caps"][d] == (lo, hi)` from `V["dimensions"]`;
- `["weights"] == V["weights"]`;
- `["limits"][n]["value"]` equal to the output's.

Add mutants A to C to the harness. Or route `_scoring` through `pinned_inputs`, a code change inside the pin, so that
`setting_rule`'s composite calls it.

### c3-3 (MINOR). A design that does exactly nothing can "exceed" the do-nothing floor by one rounding unit

**Where:** declaration 380-384, "a finalist's composite must exceed it at the point estimate"; `wave42.py` 481-490;
`null_composites`.

**Evidence.**
- **How the floor is computed:** from one unit, as 1/6 + 1/6, which is the double nearest 1/3.
- **How a design is scored:** as the mean over seeds of per-seed composites. For a do-nothing design every seed gives
  exactly that double, but `np.mean` over J copies is not always exactly that double:
  - at J = 62, 63, 128, 200, 250, 256, 500, 1000 and 2000 the mean falls one unit **below** the floor, which is safe;
  - at J = 64 it is equal, which is safe because the test is "exceed";
  - at J = 10, 11, 25-31, 100 and 125 it is one unit **above**. Over J = 1 to 5000, 1,319 values give "above".
- Measured through the public path: on `base` (J = 62) the do-nothing design scores 0.3333333333333332 against the floor
  0.3333333333333333.
- The JSON round trip also re-orders the weights (sorted keys). So a baseline re-scored from the file differs from the
  rule's own composite by up to 1.1e-16 (0 of 4 exact in the composite form, 4 of 4 in the fallback).

**The failure it allows.** Suppose a survey or H7 run uses a seed count in the "above" set, such as 100. A design that
never trades scores floor + 1.1e-16 and passes the floor that exists to remove it. Only the `not_paid_within_B` limit
and CHARTER 3.8 (c)'s long-run gate would then stop it. At the declared `TEST_SEEDS` = 1000 the error goes the safe
way, so the held-out verdict is not exposed today. The search-year screen depends on H4's J.

**Remedy (text, and one line in the survey).** Say that "exceed" means **by more than a declared tolerance**, for
example `C > floor + 1e-9`, which is far below any delta\* (the floor of delta\* is 0.01). Or compare the seed mean of
the per-seed differences C(c) - floor against 0 with the same tolerance. Add a test: a do-nothing design at J = 100
does not exceed the floor.

## 7. What I tried that found nothing

- **The JSON round trip** (`survey_view.py`). Every `limit_estimate` from the parsed output equals the rule's
  `baseline_values` exactly. `do_nothing_floor` equals the stored floor. The fallback's floor is 0.
- **The sidecar normalisation.** JSON's string escaping means no raw CR LF can sit inside a value, so the
  normalisation cannot merge two sidecars whose content differs. The blob written with `newline="\n"` is the
  normalised form.
- **`limit_per_seed_sd`.** J is taken from the first matrix's columns. `_validate` makes every matrix (n, J) for the
  baselines, so the two cannot disagree in the rule.
- **The order of the script.** The refusal-before-read test replaces every reader and asserts that none is called.
  Its mutant is killed.
- **The row schema.** Its table equals `sorted(values)`. `values_sha256` equals the canonical JSON's hash of the
  parsed rows.
- **The equivalence of the two cap sources.** They are equivalent only because `_r` is the identity. My K shows that
  a divergence would be caught.
