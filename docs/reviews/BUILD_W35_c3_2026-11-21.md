### C2-3 in detail: do the alerts equal the evaluated windows on every date?

**Yes, for the windows.** Three things hold:

   undeclared.
2. **The same bounds.** Its bounds are `SS.session_slots()` over `SS.search_days()`, as in `from_lever_space`.
3. **The same constraints.** `Space.check` runs the same `_rl3_live` and `_closed_first` functions on the same set of
   session starts.

**The start sets.** My probe (`w35c3\probe_win.py`) lists the search years' distinct start sets:

| First date | asia | london | ny |
| --- | --- | --- | --- |
| 2020-01-02 | 60 | 540 | 930 |

The autumn mismatch week falls in the second set (London 03:00 CDT). `check_declaration` builds
`C.Design(day=d)` on one date of each set (`:776-777`).

**The alert.** `_alert` builds the design for the alert's own date (`:1381-1386`) and keeps an offer only when its live
slot lies inside that date's window (`:1390`).

**P-14 cannot fire at a moment the evaluation never offers.**
- `breakout_events` (`triggers.py:351-380`) finds the events over the whole day and only then filters by
  `first <= j <= last`.
- So a P-14 built with `first = a - L`, `last = b - L` offers exactly the events whose live slot `j + L` lies in
  `[a, b]`.
- That is what the scheduler keeps from a full-span P-14 (`components.py:356`).
- This holds on condition that the evaluation's future `build` makes P-14 with the component's L, entry and k (N-c3-1).

**RL3 likewise.** Its live slot at 09:00 is held inside the window on every start set.

- Asia: 18:00, 19:00 and 19:00 CT on the same dates.

### C3-4 (MINOR). The run-order check accepts a run on a branch HEAD never merged, and cannot see an earlier off-record read

**Where:** `extended/pin_order.py:47-55` (`descends` checks pin is an ancestor of the run, never run is an ancestor of
HEAD); `playbook.py:1141-1143`.

**Evidence** (`w35c3\gitprobe`, `probe_pin.py`):
- a run commit before the pin: refused;
- a run on an unmerged side branch that descends from the pin: **accepted** (`descends(side, HEAD)` False);
- a 7-character run commit: accepted;
- outside any repository: `PinOrderError`, so refused.

**The attacks the brief asked about, all safe:**
- **A pin string elsewhere.** `-S` is restricted to `DECISIONS.md`, so an unrelated file cannot match. The text holds
  the declaration's sha256, so wherever it first appears in the log, the bytes were fixed in the run's own history.
- **Which commit `pin_commit` picks.** It does not matter for safety. If the run descends from any commit that added
  the text, the pin preceded the run. A wrong pick can only cause a false refusal.
- **A rebase.** It rewrites the pin commit, and the manifest's old run commit no longer descends from it: refused.
- **A shallow clone.** The boundary commit is treated as having added the text; it is later than the true pin, so the
  check is stricter. A run commit outside the clone fails `cat-file`: refused.
- **"Refuse when git cannot answer"** is safe: every path returns False.
- **The hook's inherited git variables** are cleared (`scripts/pre-commit:142`).

**What it allows:**
- A floor run from code that never reached master: a modified no-harm script under the declared script's name, on a
  branch that never merged.
- Git order proves the accepted run came after the pin. It cannot prove no earlier read happened, such as an
  exploratory run, or a run in another clone before the pin. That half of C2-2's remedy (the runner refuses to run
  unless its checkout pins the declaration) belongs to the runner, which does not exist.
- The expected-journey file has no order check at all (N-c3-3).

**Remedy:**
- Add `descends(root, run_commit, HEAD)`, and a test with a side-branch run.
- Write the runner-side refusal into the no-harm runner's brief as a TASK_QUEUE row.
