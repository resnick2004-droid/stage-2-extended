## (2) The single pass

**What it is.** `firms.captured_run` hands A-9 one start with Q-94's `ReplayRecorder(columns=())`. While `run_starts`
runs, it replaces `user_beside.replay` (this repository's module, not a vendored one); `_task` looks it up by its
module global. Each path is kept by (path seed, sessions), and the wrap is restored in `finally`.
- **The long run.** It is replayed under `recording_args` (ledger and day rows on). `reduce` hands A-9 a copy with them
  dropped (`replace(lp, trades=(), ...)`), so the captured object keeps its ledger.
- **The exact-length runs.** They are captured as returned, with no argument changed.
- **The adapters' accounts.** They are collected with their request logs, split by replay.

**Nothing the text requires of the second replay is missing.** The ledger (9.2's fees, 9.3's counts, item 4), the
exact-length runs' paths (A-10 reprices them, and the request oracle reads their logs), every replay's account
counters, and every request log all come from A-9's own replays. The capture needs one worker; the run uses one.

**What the capture guard catches.**
- A wrong capture, from another start, run or length. The key set must be exactly the start's runs
  (`captured_start` 284-289), and the output recomposed from the captured runs must equal A-9's bit for bit
  (`run_cell` 730-733); the recomposition reads the exact-length runs too.
- A missing exact run.
- A long run whose ledger was stripped (refused when its evaluations traded).
- A wrong count of replays' adapter accounts.
- A misaligned request log, where the plan pays out: the request oracle compares each funded account's logged nets
  with its record.

**What it cannot catch.**
- **A difference the recorder makes to A-9's outputs.** Both sides of the comparison are the recorded replays.
- **A ledger inconsistent with its own records**, which no record reads. Item 4's check of every ledger trade against
  the blocks covers part of this.

**Why the first matters.** The second build's two passes incidentally checked, on real data, that turning the ledger on
changes no output: A-9 ran without it, the direct run with it, and the comparison held them equal. Now the reading's
route has the recorder on, and:
- the identity stage runs `firms.run_plan` without capture (`identity/` unchanged);
- Q-93's identity runs no recorder;
- Q-94's own identity of the recorder ("with it on, every output equals it off") is synthetic.

So no real-data check now ties the reading's route to the identity-checked one (V1).

## (3) The break-even search sharing recompositions with the grid

`grid_rows` memoises one recomposition per price, so the grid and the three searches share them. `break_even_known`
(1136-1177) is `firms.break_even_price` step for step: the same endpoints, midpoints, tests and answer. The only
difference: where two grid prices bracket a midpoint and the grid's value above it clears the target by more than 1e-9
(or the one below falls short by more than 1e-9), the side is read off the grid instead of recomposed.

**The same answers wherever the measure is non-increasing in price.** All three measures are, exactly, under A-10's
arithmetic:
- a dearer price subtracts the price difference times each subscription paid, from every later close;
- every start pays its first evaluation on day 0;
- so each start's month-3 net falls strictly with price, and with it S5a (its p10) and the month-3 mean;
- P counts months ahead, so it can only fall or tie, and its ties are exact (a ratio of counts).

Then an inferred side is the recomposed side, and nonzero. Plain bisection would take the same branch, and could not
have returned at an exact zero there. The 1e-9 margin keeps float noise from deciding a side: S5a's steps between grid
prices are whole dollars times at least one subscription.

**The refusal** (grid values rising by more than 1e-12 between consecutive grid prices) is not reachable on real
campaigns, short of broken A-10 arithmetic, where refusing is right. Lucid's two grid prices decide little, so it
recomposes almost every midpoint: correct, and cheap.

(`keep_directs`). TS's pairing arrays are small now (13 bytes a trade).

**So** the probe's seconds per start-run, and its peaks, are floors, not estimates. That is the opposite of the
builder's earlier probe, which peaked high; the lesson is the same: a probe's campaign must be the run's campaign.
