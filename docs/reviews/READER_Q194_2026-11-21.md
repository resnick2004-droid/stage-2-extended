Inside the reader, I found no route to a held-out date before F-HT's verdict that the two changes were meant to close
and left open. Rule 1 now binds every F- purpose (`_rule1_binds`, reader.py:747-751), and it runs before rules 4, 2,

## Findings

### MINOR-1: the verdict is not tied to a held-out read that happened, or to the held-out test

- **Where:** `_test_verdict`, `extended/reader.py:846-870`.
- **Evidence:** a `heldout-verdict: F-NN @ <sha>` row counts when three things hold: the sha is a pinned sha of an
  `F-NN` path, a finalists token for `F-NN` at that sha sits between the pin and the verdict, and the verdict is newer
  than the read's window. Nothing checks that `F-NN` is the joint held-out test, or that the ledger holds `F-NN`'s
  judged read of the window. `tests/test_reader_q173.py:58-64` shows the consequence:
  1. a registered design's held-out read is admitted on the synthetic F-98's verdict (`E-982`);
  2. F-98 never read the window;
  3. then a different family, F-13, takes the window as "the joint test" (`j = H.read(...)`, admitted and ledgered).
- **Failure it allows:** any F- search that carries a finalists token for its own sha opens every `registered_design`
  held-out read before F-HT has run. This needs a row `heldout-verdict: F-<that search> @ <its sha> -- ...`, which
  could be written by mistake, ahead of time, or on a branch. The same goes for a verdict row written for F-HT before
  its clean run.
- **Forgery:** the reader can check the row's shape, its order against the pin and the finalists row, and that the
  row is committed. The last holds because `_clean_run` refuses uncommitted changes outside `results/`. The reader
  cannot check authorship. A row committed on any branch and run from that commit by `scripts/run_clean.py` passes;
  the single-writer rule is procedural.
- **Remedy:**
  - Count a `test_verdict` only when `read_ledger` holds a line with `declaration.kind == "family"`, its ref's id
    `== decl`, `declaration.sha256 == sha`, `heldout.market` the read's market, `heldout.window` the read's window, and
    `purpose` in `HELDOUT_PURPOSES`. In other words, the verdict's family must be the one that spent rule 2's window.
  - A forger would then also have to forge the append-only, history-checked ledger.
  - Optionally, also require the verdict row to appear in `git show master:DECISIONS.md`. Clean runs are `git worktree
    add --detach` checkouts, so `master` is visible from them.
  - Add a test where a verdict row exists and no held-out read is ledgered, and assert a refusal.

### MINOR-2: a read that straddles a newer window falls in E-208's base window and escapes that window's gate (latent)

- **Where:** `heldout_window`, reader.py:723-732, used by the Q-194b gate (reader.py:1048-1049), by rule 4, and by
  rule 2.
- **Evidence:** a read is assigned to the newest window row that contains all of its days, otherwise to `E-208`. My
  probe (`probe_windows.py`, P1) used the rows pin `E-980`, finalists `E-981`, verdict `E-982`, and a later window
  `E-990` covering `NQ 2025-01-02 to 2026-07-16`:
  - a read of `2025-01-02..2026-07-16` falls in `E-990` and is refused, as intended;
  - a read of `2024-01-02..2026-07-16` falls in `E-208` and is admitted by `E-982`;
  - a read of `2024-12-31..2025-01-03` also falls in `E-208` and is admitted by `E-982`.

  Widening the read gets past the "newer than the read's window opening row" clause, which
  `test_a_verdict_older_than_its_reads_window_does_not_count` tests only for a window equal to the whole judged block.
  Rule 2 has the same mechanism, which predates this change. Suppose family A spends `E-990` while `E-208` is unspent.
  Family B, holding its own finalists token, can then read `2024-01-02..2026-07-16`, which is assigned to `E-208`. No
  `E-208` line exists, so B is admitted and reads A's days a second time.
- **Why it is latent:** no window row exists in the real log, and `span` refuses everything from 2026-07-17, so any
  future window lies inside the seal.
- **Remedy:**
  - Q-194b and rule 4 should require a verdict newer than the newest opening row among every window that intersects
    the read's held-out part.
  - Rule 2 should refuse when any intersecting window was spent by another family.
  - Add a straddling-read test to each.

### MINOR-3: two verdict forms for one event; rule 4's form checks nothing

- **Where:** `_rd_after_verdict` (reader.py:807-817) and `_registered_reading_verdict` (reader.py:929-946) use the
  market form `heldout-verdict: NQ F-NN`. The Q-194b gate uses `heldout-verdict: F-NN @ <sha>`.

  unpinned and has no finalists row and no ledger read. A token is the first text of its row's third cell, so one row
  carries one form, and F-HT's verdict needs two rows:

    failure, though in the safe direction);
  - if only the market form is written, RD reads open with nothing checked, while registered reads stay shut.

  The template (`wt/wt-lit 13df998`, `prereg/TEMPLATE_heldout_test.md` section 5 item 4, "**The verdict row.**") names
  one row and gives no form. I confirmed that this is what the template says.
- **Remedy:**
  - Make rule 4 and M-3 accept the strict form, checked by MINOR-1's ledger binding. They can keep the market form or
    drop it.
  - Failing that, have the template's section 5 item 4 name both rows, in a stated order.

  returns and after Stage 2's `assert_readable`. No refused read writes a line. Rule 2 counts only `kind == "family"`

- **Every purpose path:**
  - `identity` and `registered_design` return before the family branch;
  - a capitalised `Identity` falls into the family branch and so into rule 1, the safe side;
  - choice words are refused before the pin;
  - search-year reads return before every held-out rule (tested);
  - holiday-gap-only reads are judged (`e >= SEAL_START`; tested; M12 killed).
- **Token shapes:**
  - backticked, bold, or later in the cell: not tokens (tested);
  - a 63-character sha, an empty tail, uppercase hex: not tokens, and flagged by `heldout_token_problems`;
  - the market form and the strict form do not cross-match;
  - `DECLARATION_ID`'s greedy `\d+` stops `F-1` from matching `F-12`'s pin.
- **Dates from strings** (P6): `2024-W01-2` and `20240102` parse to 2024-01-02 and are judged.
  `2023-12-29T23:59:59-06:00` parses to 2023-12-29, the choice block. The days the reader passes on are the same days
  it authorised, and `check_returned` re-checks them. The atlas walks are flattened at 15:10 CT
  (`vendor/stage2/data/README.md`), so a choice-dated row cannot carry a held-out outcome.
- **The real state:**
