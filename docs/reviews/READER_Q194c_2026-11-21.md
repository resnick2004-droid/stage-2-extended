## Findings

### MINOR-1: "made before the verdict row" is a test of the read commit's contents; a line the run wrote itself counts

- **Where:**
  - `_verdict_backed`, `extended/reader.py:902-934`
  - `_commit_has_line`, `reader.py:891-899`
  - `_dirty` excludes `results/`, `reader.py:505-510`
- **Evidence (A), the order is not proven:**
  - My probe `test_A_a_read_made_after_the_verdict_from_an_older_commit_backs_it` (in `rt194c/test_rt194c_probes.py`)
    commits F-98's pin and finalists (C0), then commits the verdict row (C1).
  - Only then does it check out C0 and make F-98's `heldout_test` read through the reader.
  - Back on master, the registered read is admitted with `test_verdict == "E-982"`.
  - The template's step 3 prescribes exactly this checkout ("a clean checkout of the held-out row's commit"). So the
    house procedure gives the reader no way to tell whether the verdict was typed before the result.
  - The same holds for any side-branch or rebased commit that lacks the line.
- **Evidence (B), a line the run wrote itself counts:**
  - The suite's own control case, `tests/test_reader_q194c.py:131` with `over == {}`, writes a hand-made line to
    `results/read_ledger.jsonl` and is admitted.
  - `_clean_run` ignores changes under `results/`.
  - So committed code running in a clean run can append an F-98 line and then pass the gate, with no F-98 read ever made.
- **Failure it allows:**
  - (A) A verdict row written before its test was run counts once the run is made from an older commit. No held-out date
    is read early: the gate still needs F-HT's ledger line. But the verdict reports nothing that had happened.
  - (B) A registered or RD read of the whole seal before any joint-test read. This needs deliberate code that writes
    ledger lines, which the merge checklist would have to miss. That is why it is MINOR, not MATERIAL.
- **Remedy:**
  - Find the first commit that adds the verdict line: `git log --reverse --format=%H -S"<line>" -- DECISIONS.md`, first
    hit.
  - Count the backing line only if that commit's committed ledger (`git show <it>:results/read_ledger.jsonl`) already
    holds it, byte for byte.
  - Also require `git merge-base --is-ancestor <line's commit> <it>`.
  - If any of these cannot be read, fail closed, as now.
  - This proves the order of read and verdict, and it rejects a line the running process appended.
  - Keep probe A as a test.

### MINOR-2: fences are parsed loosely, and only half the reader honours them; an unbalanced fence widens the gate

- **Where:**
  - `_FENCE = ^[ \t>]*(?:```|~~~)`, `reader.py:258`; it toggles on any such line (`_log_lines`, `reader.py:680-689`).
  - `decision_row` (`reader.py:427-433`) and `pins` (`reader.py:418-424`) do not look at fences. They are used by
    `_identity`, `_registered`, `_registered_heldout`, `_once`'s `repeat=`, `_registered_readings`, `_family` and
    `_exists`.
- **Evidence, my probes (all pass, i.e. the behaviour is present):**
  - **C1:** a `~~~` line inside a ``` block closes it, so a verdict row after it is a token. CommonMark treats that row
    as fenced content.
  - **C2:** a 4-space-indented ``` line toggles the state. CommonMark treats it as indented code, not a fence.
  - **C3, the unsafe direction:**
    1. F-98's read and its verdict are in place for E-208, and `E-990` opens a newer window for 2025-01-02 to 2026-07-16.
    2. A registered read of 2025 is refused, as it should be.
    3. Add one stray ``` line just above `E-990`.
    4. `E-990` is now hidden, its days fall back to E-208, and the same read is **admitted** under E-982.
  - **C4:** a fenced `heldout-read` row (E-940) admits rule 3's read after the verdict. `heldout_tokens` says it is no
    token, but `_registered_heldout` takes the line from `decision_row` and parses it on its own.
  - **C5:** an RD file pinned only inside a fence reads its judged purpose after the verdict.
  - The same `decision_row` path makes a fenced `repeat=` row or identity row count (by reading the code, not probed).
- **What limits it:**
  - `test_this_repositorys_decision_log_holds_no_malformed_heldout_token` (`tests/test_reader_heldout.py:221`) flags
    the fenced tokens of C3 and C4 on the real log.
  - It does not flag C5's fenced pin, an unbalanced fence that hides only non-token rows, or C1 and C2.
  - The guard is a test, not the reader at read time.
- **Failure it allows:** once a lead's row adds an odd fence line, the reader admits held-out reads of a window that has
  no verdict of its own (C3). Fenced example rows also admit reads (C4, C5). This is the opposite of the ruling "fenced
  rows never count".
- **Remedy:**
  - (a) At read time, refuse every judged read while the log has an unbalanced fence or a non-empty
    `heldout_token_problems`. A flaw in the log then fails closed.
  - (b) Skip fenced lines in `decision_row` and `pins`, or refuse them.
  - (c) Use CommonMark's fence rule: at most 3 spaces of indent; the closing fence of the same character and at least as
    long; a backtick info string without backticks.
  - (d) Report an unbalanced fence in `heldout_token_problems`.
  - Add a fenced pin case and a fenced E-208 case to the tests. My mutants X4 and X6 survive today (see NOTE-5).

### NOTE-1: the recorded `window` can name a window the read never touched

`authorise` (`reader.py:1178-1182`) records `window = heldout_window(...)`: the newest window holding all of the read's
days, else E-208. Probe D: with `E-990` = 2025-01-02 to 2025-06-30 and `E-991` = 2025-07-01 to 2026-07-16, a read of
2025-03-03 to 2025-09-02 is recorded under `window: "E-208"` with `windows: ["E-990", "E-991"]`.

Every check in the reader prefers `windows` (`_line_windows`), so nothing is wrong inside it. A later reader of
`heldout.window` alone would be misled. Remedy: record `window` only when it is in `windows`, or record `windows`
alone.

### NOTE-2: what "a held-out read that happened" means, stated beside the rule

- **A partial read backs the whole window.** Probe B: F-98 reads 2024-01-02 to 2024-01-31 only, and its verdict then
  admits a registered read of 2024-02-01 to 2026-07-16. This follows the ruling ("the same window"). Rule 2 already
  closes every E-208 day to other families, so nothing a test could use is exposed. State it beside the rule.
- **A crashed run counts.** `_record` writes the line before any data is read (`reader.py:1258`), so a run that crashed
  after authorising still counts as "the read". To pin this down, require F-HT's result manifest beside the line.

### NOTE-3: a window row re-opens days that were already read (by design)

`span` refuses everything from 2026-07-17. So every `heldout-window` row lies inside the seal that F-HT will have read.
Probe E: after F-98 reads E-208, `E-990` lets F-13 read F-98's 2025 days. Rule 2 trusts the lead's window row, as
documented. Registered and RD reads made under E-208's verdict before that row will also have read those days. State
this beside any later window's test.

### NOTE-4: an unreadable read commit fails closed for good

`_commit_has_line` returns True ("not shown to precede") when the commit is missing. That covers a rebase followed by
gc, a shallow clone, or a branch that was never fetched; a SHA-256 repository fails `[0-9a-f]{40}` in the same way.

This is the safe direction. But the joint test cannot be rerun: the once rule applies, the template forbids a repeat
row, and rule 2 holds. So its verdict would never count again. Normally the read commit is master's held-out row, so
this is unlikely. Remedy: tag the read's commit, for example `heldout/<F-HT>/<run_id>`.

### NOTE-6: the joint test's own read before any verdict, against the template

**What the reader enforces:**
- A finalists' token for F-HT's own sha, placed after its first pin and never in the pin's own row (`_finalists`,
  reader.py:825-854; C15 killed).
- Only purposes on F-HT's own `Judged-block reads:` line (`_family`).
- Once per purpose (`_once`).
- The window is spent against every other family, under any purpose (`_market_once`).
- Only a `heldout_test` line backs the verdict.

**What it does not enforce** (the template's scan or procedure does):
- The line naming `heldout_test` and `heldout_stress` and nothing else.
- One held-out-marked F per market.
- The read made from the held-out row's commit.
- No `repeat=` row for F-HT. A row naming F-HT passed as `repeat=` is honoured by `_once`.

The scan, `tests/test_design_search_template.py`, is on neither `wt/wt-verify` nor master.

So any pinned family with a `Judged-block reads:` line and a finalists' token can read NQ's window first and spend it.
F-03's line, for example, names `stage_C_*`. This is not a regression, and it needs a lead's token. Merge the scan, or
have the reader refuse an F- file's held-out read unless its `Judged-block reads:` line is exactly the two held-out
purposes.
