## Verdict: **must be fixed first** -- small changes in code and tests only; no re-declaration

On the pinned engine and the pinned table, the build does what the pinned text declares. I found no way in which it
changes a scorecard outcome it should not:

- the held-state rule answers the ledger's `std_winning_days - 1` to `risk_policy.account_state` alone, and to every
  other reader of the count it gives the firm's count;
- L1 goes through `_standard_eligible`, and the firm's eligibility is put back for the recorder, which is
  `last_eligible`'s only reader;
- L2 is the vendored `fast_half` arm's 0.5;
- the counters' channel changes no output;
- the identity script can run `ref` only;
- T-4's claim about the table is re-derived from the file, and it is true (my own walk agrees).

What must be fixed first:

- **M1.** The declared test T-10 is not held for the gate. Its gate toy has no table, so the held-state rule's counts
  are never carried through a gate path, and both two-worker legs are NOT CHECKED.
- **Five minors.**
  - A latent silent fall-back to the zero-day leaf.
  - No refusal if the mechanism stops firing.
  - Three counts that are not the counts 8.3 and 9.1 item 7 define.
  - A "levers off" check that is false for `ref` under the placement. A runner built on it would stop the heavy run on
    a false failure.
  - The identity prints no counts.

All of these are cheap. They should land before the runner, which is being built on this API now, takes them up.

### MINOR

**m1. An `AttributeError` raised inside the held read silently becomes `win_days` 0, the zero-day leaf that 6.3
rejects.**
`vendor/stage2/propedge/campaign/risk_policy.py:348` (`int(getattr(account, "win_days", 0))`) together with
`extended/payout_policy.py:217-258`, and lines 89-97 and 114-117, which `_held_read` calls at line 249.

- **Evidence.**
  - The engine reads the count through `getattr(..., 0)`. `getattr` with a default swallows an `AttributeError` raised
    inside a property and returns the default.
  - My pure-Python mimic of the two call sites shows it on Python 3.12.10 (Appendix A.2, last line):
    `{'win_days': 0}` at both sites.
  - `_held_read` does real work inside the getter:
    - a second `account_state` call;
    - two `rp.decide` calls;
    - on the first held read in a freshly spawned worker, `rules_from_ledger()` (a ledger load and an import).
  - The build's own refusal is a `RuntimeError`, which propagates correctly. An `AttributeError` from any of that work
    would not.
- **What it allows.** Take a held account at balance $600 with a cushion of $1,400 under `lock`. Suppose any
  `AttributeError` arises inside the read: say a table node, or a future ledger loader, that lacks an attribute. The
  table is then read at zero winning days, a leaf the pinned text calls "false to the account's state". The counter
  still records a held read of its class, so nothing shows. I know of no trigger in the pinned tree.
- **Remedy.**
  - Wrap the getter's held branch:
    `except AttributeError as exc: raise RuntimeError("REFUSED (RD-02 13.1 item 2): ...") from exc`.
  - Compute the held count once, outside the getter (at import, or from the engine's `rules`, n2).
  - Add a fault-injection test: a decide that raises `AttributeError` on a four-day state must be refused (X4 below).

**m2. If the mechanism stops firing, nothing refuses; the rule simply turns off.**
`extended/payout_policy.py:83, 223-225`.

- **Evidence.**
  - The read keys on the identity of `account_state`'s code object, and on that function reading the count through
    `getattr` in its own frame.
  - Unlike `extended/gate.py` (`VENDORED_RUN_GATE_SHA256`) and `extended/campaign.py` (`check_vendored_source`), the
    adapter pins neither `account_state`'s source nor the two call sites (`lockstep.py` 1626 and 1897).
  - Nothing in a production run checks that every held close is followed by a held read. T-4 checks this on toys
    (`pp_synthetic.py:353-357`), the run does not.
  - Today it holds: there is no second import path and no reload in the repository, and E-002 makes a new snapshot a new

- **What it allows.** Suppose a later snapshot, or a second copy of the module under another name, moves the

**m3. Three of the class's counts are not the counts that 8.3 and 9.1 item 7 define.**
`extended/payout_policy.py:291-304`; `tests/pp_synthetic.py:261` and 467.

- (a) `first_requests_held` counts **held closes**, not first requests: T-2 pins it to the number of held closes, at
  line 261. 8.3 prints "the number of first requests `lock` holds". An account held for forty closes counts forty.
- (b) Under `lock_half`, take an unlocked, unpaid account with a balance from $250 to $500. Lock holds its first request
  (`blocked`), and half would cut it below $125 too (`cell_req < payout_min`). Lines 294 and 296 count it in **neither**
  `first_requests_held` nor `half_cut_below_min`. The `lock_half` row of 8.3's mechanics therefore undercounts both
  levers in exactly the region where `lock` binds most (an account whose floor never locked has never closed at $2,000).
- (c) `cons_eligible_unpaid_sessions` counts every Consistency close that is eligible and unpaid, whatever the base
  request would be (line 303 has no `reaches`).
  - 9.1 item 7 counts "the Consistency account-sessions that start eligible and unpaid (a `half` request below $125)".
    The build also counts balances under $250, where even the maximum is below $125, so `ref` has them too and the
    number mixes `half`'s cut with the base's.
  - It counts closes rather than the sessions they start; the only difference is a last close with no session after
    it.
- **What it allows.** Printed mechanics that answer a different question from the one 8.3 asks: (a) overstates, (b)
  understates, and (c) mixes the lever's effect with the base's.
- **Remedy.**
  - Carry (a) both per account (accounts whose first request was ever held) and per close, each labelled.
  - Give a close held by both levers to `lock`, or to a third count.
  - Restrict (c) to closes at which the base's request reaches the minimum, keeping the wider count apart if it is
    wanted.
  - Adjust T-2 and T-5 to match.

**m4. "Levers off" is tested as every counter at zero. Two of the counters are the engine's own Consistency counts,

`extended/payout_policy.py:172-180` (`total_counters`); `identity/pp_identity.py:80-82`; `tests/pp_synthetic.py:577-578`.

- **Evidence.**
