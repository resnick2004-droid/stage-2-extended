### (g) Cost: what the text requires, what it permits, what the runner adds

**What the text requires.**
- 7.3: 30 or 34 replays, "each runs both arms, every start, the long replay and U1's exact-length runs".
- 7.4: the 27 ladder replays with Q-17's exact-length rule, and the 16 gates at 500 paths, point and bound, with the
  zero-edge twin.

  every start.
- 14.1 and 9.1 item 1: the runner is U1's replay through U1's own task with A-1's arguments, through A-9 (the identity

**What it does not require.** A second replay, or any equality check. The runner replays every scorecard start twice:
once through A-9 for the outputs, once directly for the records that 9.2, 9.3 and A-10 read. The equality check
exists to show the second replay is the first.

**On a subset.** A declared subset of starts for the equality check is not forbidden by any line, since the text never
names the check. But it would save almost nothing: the direct replays would still run on every start, because 9.2, 9.3
and A-10 read them. Only the comparison would be dropped, and the comparison is cheap. It would also leave DayTraders'
headline, and every 9.2, 9.3 and A-10 number on the unchecked starts, resting on replays not shown to be the runner's.

**The route the text plainly supports.** One pass through A-9, with each replay's records kept from A-9's own replays
in the same process:
- the long run's ledger through A-9's own `recorder` seam (Q-94, whose identity holds the outputs bit for bit);
- the exact-length runs' paths kept by an in-process capture of `user_beside.replay`'s return, which changes no
  argument.

That removes the second replay and makes the comparison unnecessary. It is a build change under the unchanged text; it
needs its own synthetic test (outputs with and without the capture, bit for bit), and `replay_records.py` added to
Q-104's list.

**What the runner adds beyond the text, measured on the toy where possible (B2: an order of magnitude, not a
forecast).**
1. **The second replay of every scorecard start**, long and exact-length (about x2 on the scorecard's engine work), and
   of the six DayTraders ladder replays.
2. **The break-even bisection at $0.01, run separately for each of three measures** (`grid_rows` 1005-1021): about 17
   recompositions each. With the 10 to 13 grid prices, each start's output is recomposed about 60 times per grid cell

   replays, so the grid and bisection add about one more replay pass per grid cell there. The text sets no tolerance; a

3. **The twin call runs two identical arms** (both on the zero-edge blocks at a zero shift; one is discarded), so each
   corner's gate does four arm-runs where three are read. This is built into A-8's `run_gate`; removing it means

4. **Quick Pay's four gates at one worker** (`rd01_reading.py` 365): wall time, because its point-holding class cannot

**Memory** (m7's second half): every row of all three stages is held in memory until the end, because `fc_reading.csv`

**m2. G-10's "drained" counts accounts that ended, not only accounts left drained.**
`firm_reading.py` 581 counts any account not breached whose last cushion is below one micro at the smallest stop.
- A Quick Pay account at the ceiling's lenient end withdraws its whole balance and ends with a cushion of zero, so it is
  counted "drained".
- So is an account at the ceiling's strict end, or at Fast Pass's fifth request, whose cushion happens to be small.

5.6 means an account "drained below its trading size and idle", holding a seat.

*Remedy.* Count only accounts still open at the replay's end (or at its horizon), or say that the ceiling's and the
fifth request's endings are excluded.

**m3. Two of the builder's readings lack an anchor.**
- **The uncapped ladder** (`uncapped_ladder_differs` 452-483) rebuilds each Fast Pass funded trade's size under an
  uncapped ladder. There is no control that the same rebuild under the actual ladder gives every trade's own contracts,
  so any gap in the rebuild would count as "differs". *Remedy:* run the rebuild with the plan's own ladder first, and
  refuse unless every trade reproduces.
- **The menu's start-year P** (`firm_menu.py` 219-237) is the long replays' months ahead, labelled "the exact-length
  runs not substituted". It differs from the card's P wherever an exact run differs, so the years need not agree with
  the blocks. *Remedy:* write U1's own per-start months ahead (through `Views`) in the start table, and read the years
  from it.

**m4. The twin is zero-edge at the log's costs, not the plan's.**
`zero_edge_blocks` shifts each R to a zero mean of the log's net outcomes. The plans then re-price each trade's fee at
their own schedule. At DayTraders' lenient fee basis a micro costs $0.20 a round turn less than the log's ($1.02
against $1.22). That is about +0.003 R a trade at P-16's 150-tick stop, and about +0.008 R at P-14's 50-tick stop. So
the DT-16-l and DT-14-l twins carry a small positive edge, and 9.2's premise ("a fair game") holds only approximately
there.

D-324's re-pricing at the contracts held moves every plan's twin slightly off zero in both directions; the lenient
DayTraders micro is the largest move up. A false refusal is unlikely, given the rules' slack under $2,000 and the 99.9 %
interval. But it is possible, and it would come after all three reads are spent.

*Remedy.* Price the twin at the log's own per-trade fees (`fee_schedule` None: "the log's fee stands"), so it is
exactly zero-edge and tests the contract's mechanics. Say so in the manifest.

**m5. The twin's pass rate counts every evaluation bought, resolved or not.**
`twin_measures` 1058 divides by every evaluation, including those unresolved at the gate's horizon or closed for
inactivity. That lowers the rate and weakens the oracle; T-7 used resolved evaluations only.

*Remedy.* Divide by the resolved evaluations (passed or failed), with the others counted beside.

**m6. Item 3's and item 4's menu readings drop starts with no value before windowing.**
`firm_menu.py` 330-331 and 394-395 window the remaining series. 10.2 item 1 cuts "the block's starts in order ... into
consecutive h-start windows". For measures undefined on some starts (cash before a first payout never reached, the
fall after a break-even never made), the windows then span more than h starts, and kept windows can share sessions:
the very defect 10.2's window rule exists to prevent. Separately, the coverage label is missing wherever the run did
not compute that (h, n_w) ("coverage not computed by the run at this setting"), but 10.2 item 7 labels every reading.

*Remedy.* Window on start positions and average the defined values in each window, or print no interval for a series
with gaps. Compute coverage at every setting the menu uses: the n_w are known from the block sizes before the menu
runs.

**m7. The later purposes are not pre-checked, and the run holds everything to the end.**
- `main` ledgers `firm_scorecard` before it learns whether `firm_ladder_beside` or `firm_gate_beside` would be refused
  (for example, already ledgered). RD-02's runner pre-checks all three with `reader.authorise`, which reads and writes
  nothing (E-098).
- Holding every row in memory to the end ((g) Memory) is the second half.

*Remedy.* Call `reader.authorise` for all three purposes before the first `authorise_engine_read`. Spill each finished
cell's rows to the resume folder and build the frames from it at the end.
