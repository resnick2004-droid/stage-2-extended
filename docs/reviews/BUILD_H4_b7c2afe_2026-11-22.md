#### M-4. Independent scalar oracle (`verify_race_trade_row`) will false-kill `H4-B` and `audit` on two valid race-arm cases
- **Where**: `extended/h4_audit.py:307-339`, `383-384`, `435-493`
- **Evidence**:
  - **(a) Floor-clip refusal on time exits (`h4_audit.py:383-384`)**: For a cushion-bound `walk` or unarmed `move` trade ending at its time limit (`kc == 0`, flatten, where `xf_ticks = 2 > xs_ticks = 1`), `three_way_baseline.py:483,503` logs the pre-clip value `out = -e + v*d - xf`, which lies in `[-room - (xf - xs), -room)` whenever `v` lands in `(-L_ticks, -L_ticks + (xf - xs)/d)` (and `lockstep.py` then clips to `-room`, generating Template v3's time-exit clip credit). Line 383 unconditionally refuses `out_logged < -room - tol`. Verified in Probe 2b on a real `TB.RaceOver` call: `lane=1, out=-17.0, room=16.5` raised `H4OracleRefused: booked out -17.0 passes floor -room=-16.5`.
  - **(b) `SNAP` lattice-boundary divergence (`h4_audit.py:314-315` vs `three_way_redraw.py:179,326-328`)**: `three_way_redraw._ends_lanes` computes the last interior lattice index with `SNAP = 1e-9` (`ceil(L / s - 1e-9) - 1`), whereas `walk_scalar_independent` tests exact `Fraction` inequalities `pos - s <= -L` / `pos + s >= G` without `SNAP`. Whenever floating-point division (`(room - e - xs)/d` or `(need + e + xt)/d`) lands `1e-15..1e-10` above a multiple `k * s`, the oracle disagrees on the last step's exit code and cost. Verified in Probe 1b: `L = 12.0 + 1e-13, s = 4, n = 3, us = [0.9, 0.9, 0.9]` gave `RD = (-12.0000000000001, 'stop')` vs `HA = (-12.0, 0)` (different exit code and cost!).
  - **(c) String `"0"` truthiness (`h4_audit.py:456`)**: `bool(row["move_moved"])` evaluates `"0"` as `True` if rows are read via `csv.DictReader` instead of `pd.read_csv`.
- **Remedy**:
  - In `verify_race_trade_row`, keep strict `out_logged >= -room - tol` for `race`, `fill_fail`, and `kc in (1, -1, 3)`, and for `law in ("walk", "move")` with `kc == 0` enforce `out_logged >= -room - (xf - xs) - tol` while recording the time-exit clip credit `max(0.0, -room - out_logged)` beside (`prereg/H4_rebaseline.md:257`).
  - Match `three_way_redraw`'s `SNAP = 1e-9` interior-index rule `(u_, d)` in `walk_scalar_independent` while keeping exact `Fraction` arithmetic for the two-point race probabilities and zero-EV check.
  - Parse `move_moved` via `bool(int(float(row["move_moved"])))`.

#### M-6. `peak_month_1..3` off-by-one excludes month close `21*m`, corrupting W42-R1 `REQUIRED` columns and `readings_sha256`
- **Where**: `extended/h4_audit.py:600-605`
- **Evidence**: Line 604 computes `UM.spent_before(rel[: h_m + 1], h_m)` = `max(0, -min(rel[:h_m]))`, **excluding close `h_m`** (`21`, `42`, `63`). By contrast, `docs/MEASURES.md` (B-2, section 2), `extended/user_measures.py:248-261` (`peak_through`, `peak_by_month`), `extended/user_beside.py:620`, and `extended/wave42.py:354-357` define `peak_month_m` as peak out-of-pocket **through** close `21*m` inclusive (`max(0, -min(rel[:h_m + 1]))`). Whenever a fee/purchase on close 21, 42, or 63 creates a new trough, `peak_month_m` is understated in `h4_units_*.csv` and `h4_w42_input.csv`, changing `readings_sha256` and Wave 4.1 inputs (while `P_B` itself happens to be shielded because `net_month_m > 1e-6` implies `rel[h_m] > 0`).
- **Remedy**: Replace `UM.spent_before(rel[: h_m + 1], h_m)` with `UM.peak_through(rel, h_m)` (equivalently `JM.peak_oop(rel, h_m)`), and add a unit test with a new low at close 21.

#### M-7. Measure (11) `deepest_fall_after_be_252` computes fall below `$0` instead of drawdown from running high
- **Where**: `extended/h4_audit.py:695-700`
- **Evidence**: Line 699 computes `deepest = float(max(0.0, -float(np.min(after))))` (excursion below `$0`), whereas `extended/user_measures.py:152-157` (`UM.deepest_fall_after`, Measure (11)) defines it as `max(np.maximum.accumulate(r) - r)` from the break-even close onward. - **Remedy**: Delegate directly to `UM.fell_back(rel[: year_win + 1], float(be_252))` and `UM.deepest_fall_after(rel[: year_win + 1], float(be_252))`.
